\section{为什么要用 GPU}

GPU 与 CPU 的根本区别在设计目标——CPU 为单线程延迟服务，GPU 为总吞吐服务。此 Module 关注延迟/吞吐、SIMD/SIMT 等相关概念。

\begin{reading}
Guide 1.1、1.2.1--1.2.2；LCPU 讲义\footnote{\url{https://github.com/interestingLSY/CUDA-From-Correctness-To-Performance-Code/blob/master/lecture.md}} Part 0。
\end{reading}

\prob{1.1}{CONCEPT}
判断对错，可以顺带补一句理由。
\begin{enumerate}[label=(\alph*)]
  \item 一块标称 100 TFLOPS 的 GPU，执行单条指令的延迟一定低于 5 GHz 的 CPU。
  \item HBM 的“高带宽”指大块连续访问时的吞吐，零散的随机访问达不到标称值。
  \item 严格串行的迭代算法（每步依赖上一步的结果），即使换一块算力更强的 GPU 也快不了多少。
  \item “算力 1000 TFLOPS”意味着每次运算的延迟是 $10^{-15}$ 秒。
\end{enumerate}

\begin{answer}
(a) 错。TFLOPS 描述大量并行运算的总吞吐，不代表单条指令延迟。\\
(b) 对。标称带宽依赖连续、合并且并发度足够高的访问。\\
(c) 对。严格的数据依赖链无法利用 GPU 的大规模并行吞吐。\\
(d) 错。1000 TFLOPS 是每秒总运算次数，不是一次运算的延迟。
\end{answer}

\prob{1.2}{CONCEPT}
Session 1 讲座里提过“N 方过百万”这个例子。总计算量 $10^{12}$ FLOP 在当代 GPU 上的运算时间大概是毫秒级，那为什么一个严格在线的串行算法仍然做不到几秒内跑完？（从“延迟”和“吞吐”的角度考虑）

\begin{answer}
峰值 FLOPS 依赖大量独立运算同时在途。严格在线算法的下一步必须等待上一步，
无法铺开足够并行度，只能逐次承担单步指令和访存延迟，因此总时间由依赖链长度
乘以单步延迟决定，而不是由峰值吞吐决定。
\end{answer}

\prob{1.4}{CONCEPT}
SIMD 与 SIMT 的区别？另：判断正误——Nvidia GPU 在 Volta 之后每个线程有独立的 program counter，所以 branch divergence 不再有性能代价。

\begin{answer}
SIMD 由一条显式向量指令操作多个数据元素；SIMT 暴露多个标量线程，硬件把
线程组成 warp 共同取指和发射。判断为错：独立 program counter 改善了线程级
调度和同步语义，但同一 warp 走不同分支时仍需按 active mask 执行各条路径，
divergence 的串行化代价仍然存在。
\end{answer}

\prob{2.2}{CONCEPT}
为下列五个场景选择正确的修饰符（如 \texttt{\_\_global\_\_} 等）。
\begin{enumerate}[label=(\alph*)]
  \item 在 GPU 上执行、由 CPU 侧启动的 kernel 函数。
  \item 只会被 kernel 调用的辅助函数。
  \item host 和 device 代码都要调用的小工具函数。
  \item 整个 kernel 运行期间不变、所有线程都要读的系数表。
  \item block 内线程共享的暂存数组。
\end{enumerate}

\begin{answer}
(a) \texttt{\_\_global\_\_}；(b) \texttt{\_\_device\_\_}；
(c) \texttt{\_\_host\_\_ \_\_device\_\_}；
(d) \texttt{\_\_constant\_\_}；(e) \texttt{\_\_shared\_\_}。
\end{answer}

\prob{2.4}{CONCEPT}
判断对错，可以顺带补一句理由。
\begin{enumerate}[label=(\alph*)]
  \item \texttt{vectorAdd<<<...>>>(...)} 这条语句返回时，kernel 一定已经执行完毕。
  \item 同一个 stream 里，\texttt{cudaMemcpy}（device 到 host）会等它前面的 kernel 全部完成后才开始拷贝。
  \item kernel 内部的非法访存，会在启动语句处同步地报出来。
\end{enumerate}

\begin{answer}
(a) 错，kernel launch 通常异步返回。\\
(b) 对，同一 stream 保持提交顺序，同步的 D2H copy 会等待前序 kernel。\\
(c) 错，非法访存通常在后续同步或错误检查 API 处暴露。
\end{answer}

\section{SIMT 执行}

SIMT 给每个线程“独立执行”的表象，硬件却按 32 线程一组共享 instruction fetch 和 issue（取指和发射）。此模块三个实验的主题分别为“divergence 的代价”、“\texttt{\_\_syncthreads} 的必要性”、“block 之间为什么无法同步”。

\end{reading}

\begin{answer}
预测按 warp 对齐版本约快 2 倍。实测：warp 内分支 1.591 ms，按 warp

\end{answer}

\end{lookback}

\begin{lookback}
本模块的八道题围绕同一个问题展开：数据放在哪一层，以什么模式去取。prob 4.1 给出一幅静态的存储层次地图，prob 4.2 与 4.3 在同一段 stencil 上切换存储位置，prob 4.5 与 4.6 在同一个直方图统计上做同样的变换，prob 4.7 和 4.8 则分别量化访问模式与可并发的请求数量。

有三点值得单独记下。其一，优化只在真正的瓶颈处生效。prob 4.3 是一个刻意安排的负结果：教科书罗列的手段用在了不构成瓶颈的地方，收益为零。避免这类空转，需要先估算再动手，估算可以依赖 arithmetic intensity 与 roofline 模型，后面的 session 会展开。其二，你在 prob 4.8 (b) 写下的那句解释有一个正式的名称——Little 定律：维持某一吞吐量所需的在途请求数，等于吞吐与延迟的乘积。其三，occupancy 本身是手段，不是目标。它高只说明调度器有足够多的 warp 可以切换，并不自动保证访存效率；反过来，低 occupancy 配合足够的指令级并行，同样能跑满内存带宽。Volkov 的 \textit{Better Performance at Lower Occupancy}（GTC 2010）是这一观点的经典论述。
\end{lookback}

判断对错，可以顺带补一句理由。
\begin{enumerate}[label=(\alph*)]
  \item 同一个 stream 里的操作按提交顺序执行。
  \item kernel 启动后，host 代码立刻继续往下执行。

\begin{lookback}

再下一步，异步自然会引出重叠：多 stream、数据拷贝与计算的并发、用 CUDA Graph 把整张任务图一次性提交。这些内容会放在后续 session 里展开，这里只需要建立起一个清晰的 mental model：host 只管提交，device 只管执行，两条时间线各自推进。
\end{lookback}

\prob{6.1}{CONCEPT}

\begin{enumerate}[label=(\alph*)]
  \item tile 是显存里的一块可变区域，kernel 通过指针直接改写它。
  \item 对 tile 的一次运算（如两个 tile 相加）由编译器映射到 block 内的多个线程上执行。

\begin{lookback}
Module 0 里那个“能跑就行”的 hello，现在被拆开重新看过：源码经 nvcc 分成 host 和 device 两路，device 端产出 PTX 与 SASS，一并打包进 fatbin；运行时 driver 再从中挑选合适的版本，或者对 PTX 做 JIT。

这一模块的实用意义在交付环节。“编译通过”和“能在目标卡上跑起来”是两回事，后者是部署中最常撞上的墙。当你把一个 GPU 程序交付给别人，至少需要说清楚：它支持哪些 compute capability，fatbin 里包含了哪些架构的 SASS，有没有 PTX 兜底，以及首次运行的 JIT 开销落在哪里。写 kernel 与发布软件是两种视角，而这里正是二者的交界。
\end{lookback}

  \item TileLang：\texttt{kernels/tilelang\_matmul.py}（即 prob 7.6 补全的成品），调 \texttt{bench()} 的 \texttt{block\_M / block\_N / block\_K / num\_stages}，记录实测数据。

试分析性能差距的原因，特别是：TileLang 的控制粒度比 Triton 更细，为什么在这组测试里反而略慢？

\begin{answer}
\textbf{测试环境：}RTX 4060 Laptop GPU，compute capability 8.9，24 SM；
$M=N=K=2048$，Triton/TileLang 使用 fp16 输入、fp32 累加。

\textbf{Naive CUDA：} \texttt{BS=8/16/32} 的 \texttt{sm\_89} 版本均编译
成功，但运行时在第一次 \texttt{cudaMalloc} 处返回
\texttt{cudaErrorNoDevice}。当前环境中 PyTorch/Triton 可以访问 GPU，而独立
CUDA Runtime 进程不能枚举设备，因此没有记录不可信的 naive GFLOPS。

\textbf{Triton benchmark：}
\begin{center}\small
\begin{tabular}{@{}lrr@{}}
\toprule
配置 & 平均耗时 (ms) & TFLOPS \\
\midrule
\texttt{32x32x32} & 1.239 & 13.9 \\
\texttt{64x64x32} & 1.237 & 13.9 \\
\texttt{128x64x32} & 1.184 & 14.5 \\
\texttt{128x128x32} & 1.245 & 13.8 \\
\texttt{128x128x64} & 1.422 & 12.1 \\
\texttt{64x64x64} & 1.135 & 15.1 \\
\texttt{cuBLAS} & 1.080 & 15.9 \\
\bottomrule
\end{tabular}
\end{center}
正确性测试为 \texttt{2 passed}；该组配置中 Triton 最快的是
\texttt{64x64x64}。

\textbf{TileLang benchmark：}
\begin{center}\small
\begin{tabular}{@{}lrrr@{}}
\toprule
配置 & threads & 平均耗时 (ms) & TFLOPS \\
\midrule
\texttt{64x64x32, stages=1} & 128 & 1.204 & 14.3 \\
\texttt{64x64x32, stages=3} & 128 & 1.064 & 16.1 \\
\texttt{128x128x32, stages=3} & 128 & 1.116 & 15.4 \\
\texttt{128x128x64, stages=3} & 256 & 1.216 & 14.1 \\
\texttt{128x256x64, stages=1} & 256 & 1.609 & 10.7 \\
\bottomrule
\end{tabular}
\end{center}
TileLang matmul 正确性测试为 \texttt{1 passed}。原先
\texttt{128x256x64, stages=3} 需要 147456 B 动态 shared memory，超过本卡
100 KB/block 的限制，已改为 \texttt{stages=1} 后可运行。

tile 大小决定每个 program 的数据复用、global memory 访问形状、寄存器压力、
shared memory 用量和 occupancy；\texttt{BLOCK\_K} 或 \texttt{num\_stages}
增大不一定更快。流水深度为 3 的 \texttt{64x64x32} 在本次测量中隐藏了更多
搬运延迟，但较大的 \texttt{128x256x64} 又因 tile 过大而变慢。naive CUDA
每个线程只计算一个输出元素，沿 $K$ 维重复从 global memory 读取，缺少 tile
复用和 Tensor Core 路径，因此理论上会显著落后于两种 tiled 实现；本机尚未
取得它的可执行测量值。
\end{answer}

本次数字来自各自 \texttt{bench()} 的单次配置扫描，不能替代 profiler 分析；
结果也会随 GPU 时钟、驱动、CUDA/Triton/TileLang 版本变化。
